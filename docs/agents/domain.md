# Domain Docs

วิธีที่ engineering skills ควรอ่านเอกสาร domain ของโปรเจกต์นี้เมื่อสำรวจ codebase
โปรเจกต์นี้เป็น **single-context**: ใช้ `GLOSSARY.md` ที่ root และ ADR ใน `docs/adr/` จุดเดียว

## ก่อนสำรวจโค้ด ให้อ่านไฟล์เหล่านี้

- **`GLOSSARY.md`** ที่ repo root
- **`docs/adr/`**: อ่าน ADR ที่เกี่ยวกับพื้นที่ที่จะลงมือทำ

ถ้าไฟล์ใดไฟล์หนึ่งยังไม่มี **ทำต่อไปเงียบๆ** — อย่าทักเรื่องการไม่มี และอย่าเสนอให้สร้างล่วงหน้า
skill `/domain-modeling` (ถูกเรียกผ่าน `/grill-with-docs` และ `/improve-codebase-architecture`) จะสร้างไฟล์เหล่านี้ตามต้องการจริงเมื่อมีศัพท์หรือการตัดสินใจที่ถูกทำให้ชัดเจนแล้วเท่านั้น

## โครงสร้างไฟล์

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
└── src/
```

## ใช้ศัพท์ตามที่ glossary กำหนด

เมื่อ output ของคุณกล่าวถึง concept ของ domain (ในชื่อ issue, ข้อเสนอการ refactor, hypothesis, หรือชื่อเทสต์)
ให้ใช้คำตามที่นิยามไว้ใน `GLOSSARY.md` — อย่า drift ไปใช้คำพ้องที่ glossary ระบุว่าไม่ใช้

ถ้า concept ที่คุณต้องการยังไม่อยู่ใน glossary นั่นคือสัญญาณว่า: หรือคุณกำลังสร้างศัพท์ที่โปรเจกต์ไม่ได้ใช้ (ลองทบทวน) หรือมีช่องว่างจริง (จดไว้สำหรับ `/domain-modeling`)

## Flag เมื่อขัดกับ ADR

ถ้า output ของคุณขัดกับ ADR ที่มีอยู่ ให้ชี้ให้เห็นอย่างชัดเจน อย่า override เงียบๆ:

> _ขัดกับ ADR-0007 (event-sourced orders) แต่ควรพิจารณาเปิดใหม่เพราะ…_
