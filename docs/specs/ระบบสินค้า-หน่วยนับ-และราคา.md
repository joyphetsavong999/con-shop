# สเปก: ระบบสินค้า หน่วยนับ และราคา

## Problem Statement

ร้านวัสดุก่อสร้างหนึ่งแห่งขายทั้งลูกค้าปลีก (เจ้าของบ้าน ผู้ทำงานทั่วไป) และลูกค้า B2B (ผู้รับเหมา บริษัทก่อสร้าง) ในระบบเดียวกัน แต่สินค้าของร้านมีหน่วยนับที่ซับซ้อนจนไม่มีเครื่องมือทั่วไปรองรับ

- ปูนซีเมนต์ขายเป็นถุง (หน่วยพื้นฐาน) แต่ผู้รับเหมาสั่งเป็นพาเลต
- กระเบื้องขายเป็นกล่อง แต่ลูกค้าคำนวณปริมาณที่ต้องการเป็นตร.ม.
- เหล็กขายเป็นเส้น ลูกค้าคิดน้ำหนักเป็นกิโลกรัม
- มีราคาปลีก ราคาส่ง และราคาที่ตั้งเฉพาะรายลูกค้า B2B

ปัจจุบันร้านคิดราคาและตัดสินว่าลูกค้าเข้าเกณฑ์ราคาส่งหรือไม่ ด้วยมือหรือสเปรดชีตที่ตัวเอง ผลที่ตามมาคือ:

1. **ปริมาณที่ลูกค้าต้องการไม่ค่อยเป็นจำนวนเต็มของหน่วยขาย** เช่น ลูกค้าคิด 20 ตร.ม. ซึ่งเท่ากับ 13.89 กล่อง ร้านต้องตัดสินใจเองว่าจะปัดขึ้นหรือลง และแต่ละคนอาจตัดสินกันคนละทาง
2. **ไม่ชัดว่าของที่เหลือขายได้หรือไม่** ถ้าเหลือปูน 35 ถุง ผู้รับเหมาสั่ง 1 พาเลต (40 ถุง) จะขายได้หรือไม่ ร้านแต่ละทางตอบคนละแบบ
3. **ลูกค้าไม่รู้ว่าตัวเองจะได้ราคาส่งหรือไม่** ร้านต้องตัดสินใจเองว่าจะให้ราคาไหน แล้วแจ้งปากคำ ลูกค้าที่กลับมาซื้อครั้งถัดไปอาจได้ราคาต่างจากเดิม
4. **ราคาผิดเสียเงินจริง** การคิดเศษและการคูณแบบมือทำผิดพลาดได้ง่ายในออเดอร์ที่มีหลายหน่วยขาย
5. **แคตตาล็อกระเบิดเป็นหลายรายการซ้ำ** กระเบื้องสีขาวกับสีเทา ถ้าแยกเป็นคนละสินค้า ผู้ดูแลต้องสร้างแยกทีละรายการ แต่ถ้ารวมเป็นสินค้าเดียว ราคาและสต็อกก็ปนกัน

## Solution

สร้างโมเดลสินค้าและหน่วยนับที่ยึดหลัก **หน่วยพื้นฐานหนึ่งหน่วยต่อหนึ่งสินค้า** และแยกความหมายของ "หน่วยที่ขาย" ออกจาก "ภาชนะที่เก็บ" แล้วให้ทุกการตัดสินใจเรื่องราคาไหลผ่าน**จุดเดียว** คือการคิดราคารายการ

หลักการที่ยึด:

- **สินค้า** คือวัสดุหนึ่งชนิด ปูนซีเมนต์คือสินค้าเดียว ไม่แยกเป็น "ปูนถุง" กับ "ปูนพาเลต"
- **หน่วยพื้นฐาน** คือหน่วยเดียวที่สินค้านั้นถูกขายและนับสต็อก
- **หน่วยขาย** คือตัวคูณจำนวนเต็มของหน่วยพื้นฐาน ไม่ใช่ภาชนะที่ต้องขายครบก้อน
- **หน่วยวัด** (ตร.ม. กก.) เป็นข้อมูลช่วยคินให้ลูกค้า ไม่ใช่หน่วยที่ขาย
- **ขายจำนวนเต็มเสมอ** ไม่มีการสั่งเป็นเศษ ระบบจึงไม่มีกฎปัดเศษที่ไหนเลย
- **ราคาทุกตัวเป็นต่อหน่วยพื้นฐานเสมอ** และเลือกชั้นราคาตามลำดับความสำคัญ
- **เกณฑ์ปริมาณและส่วนลดปริมาณคิดจากจำนวนหน่วยพื้นฐานที่ซื้อจริง** ไม่ขึ้นกับว่าลูกค้าเลือกหน่วยขายใด

ผลคือลูกค้าที่ซื้อ 80 ถุง ได้ส่วนลดเดียวกับคนที่ซื้อ 2 พาเลต เพราะได้จำนวนหน่วยพื้นฐานเท่ากัน และหน่วยขายเป็นเพียงตัวช่วยกรอกจำนวนให้สั้นลง

## User Stories

### ลูกค้าปลีก (เจ้าของบ้าน ผู้ทำงานทั่วไป)

1. As a ลูกค้าปลีก, I want to เห็นว่าสินค้านั้นขายเป็นหน่วยอะไร, so that ฉันเข้าใจว่าต้องสั่งอะไร
2. As a ลูกค้าปลีก, I want to เห็นความสัมพันธ์ระหว่างหน่วยขายกับหน่วยวัด เช่น "1 กล่อง = 1.44 ตร.ม.", so that ฉันตัดสินใจได้ว่าต้องซื้อกี่กล่อง
3. As a ลูกค้าปลีก, I want to เลือกจำนวนหน่วยขายที่ต้องการได้ เช่น 2 กล่อง, so that ฉันสั่งซื้อได้โดยไม่ต้องคิดแปลงหน่วยเอง
4. As a ลูกค้าปลีก, I want to เห็นราคาสุทธิของทั้งรายการตั้งแต่ก่อนกดสั่งซื้อ, so that ฉันไม่มีทางเจอยอดที่ไม่คาดคิด
5. As a ลูกค้าปลีก, I want to เห็นจำนวนหน่วยพื้นฐานที่เป็นเท่ากับหน่วยขายที่ฉันเลือก, so that ฉันตรวจสอบความถูกต้องได้
6. As a ลูกค้าปลีก, I want to สั่งซื้อเหล็กเป็นจำนวนเต็มของเส้นได้ โดยเห็นน้ำหนักรวมเป็นตัวเลขช่วยคิน, so that ฉันซื้อได้โดยไม่ต้องแปลงกิโลกรัมเอง
7. As a ลูกค้าปลีก, I want to เข้าใจว่าระบบรับเฉพาะจำนวนเต็ม ไม่รับเศษ เช่น 0.5 กล่อง, so that ฉันไม่ใส่ค่าที่ระบบปฏิเสธแล้วงง
8. As a ลูกค้าปลีก, I want to เห็นราคาปลีกของสินค้า, so that ฉันเทียบกับราคาที่เห็นตามท้องตลาดได้
9. As a ลูกค้าปลีก, I want to ได้ราคาเฉพาะลูกค้าที่ร้านตั้งไว้ให้ฉัน, so that ฉันได้ราคาที่ร้านยอมรับกับฉันเป็นการส่วนตัว
10. As a ลูกค้าปลีก, I want to ถ้าฉันซื้อเยอะพอแต่ยังไม่เข้าเกณฑ์ราคาส่ง ระบบบอกได้ตรงๆ ว่าขาดอีกเท่าไร, so that ฉันตัดสินใจได้ว่าคุ้มไหมที่จะสั่งเพิ่ม

### ลูกค้า B2B (ผู้รับเหมา บริษัทก่อสร้าง ฝ่ายจัดซื้อ)

11. As a ผู้ซื้อ B2B, I want to เลือกหน่วยขายได้ว่าจะสั่งเป็นถุงหรือพาเลต, so that ฉันกรอกจำนวนได้สั้นลงเมื่อสั่งปริมาณมาก
12. As a ผู้ซื้อ B2B, I want to ได้ราคาส่งเมื่อสั่งครบเกณฑ์ปริมาณ, so that ฉันได้ราคาตามที่ตกลงกับร้าน
13. As a ผู้ซื้อ B2B, I want to ได้ส่วนลดปริมาณเมื่อซื้อหลายหน่วยพื้นฐานพอตามเกณฑ์, so that ฉันได้ราคาถูกลงเมื่อสั่งมาก
14. As a ผู้ซื้อ B2B, I want to ได้ส่วนลดเดียวกันไม่ว่าจะสั่งเป็นถุงหรือพาเลต, so that ฉันไม่ต้องคำนวณว่าต้องสั่งหน่วยไหนถึงจะได้ส่วนลด
15. As a ผู้ซื้อ B2B, I want to เห็นว่าฉันกำลังจะได้ราคาเฉพาะลูกค้าทับราคาส่งอยู่หรือไม่, so that ฉันเข้าใจว่าทำไมราคาของฉันถูกกว่าลูกค้า B2B รายอื่น
16. As a ผู้ซื้อ B2B, I want to สั่งของเหลือที่มีไม่ครบพาเลตได้เมื่อของในร้านไม่พอ, so that ฉันไม่ต้องรอพาเลตก้อนใหม่หรือยกเลิกออเดอร์
17. As a ผู้ซื้อ B2B, I want to เห็นจำนวนหน่วยพื้นฐานของออเดอร์ทั้งหมดรวมกัน, so that ฉันตรวจสอบได้ว่าจำนวนถูกต้องตามที่ร้านนัดไว้
18. As a ผู้ซื้อ B2B, I want to ทราบจำนวนเงินสุทธิที่แน่นอนก่อนยืนยันออเดอร์, so that ฉันใช้เป็นเอกสารขออนุมัติงบประมาณได้

### ฝ่ายขายหน้าร้าน / พนักงานรับออเดอร์

19. As a พนักงานขาย, I want to กรอกรายการสั่งซื้อให้ลูกค้าที่อยู่หน้าเคาน์เตอร์โดยเลือกหน่วยขายได้, so that ฉันบันทึกออเดอร์ได้เร็วโดยไม่ต้องคำนวณเอง
20. As a พนักงานขาย, I want to เห็นยอดที่ระบบคำนวณเป็นอัตโนมัติ, so that ฉันไม่ต้องเผื่อความผิดพลาดจากการคิดเอง
21. As a พนักงานขาย, I want to เห็นชั้นราคาที่ถูกเลือกใช้ในแต่ละรายการ, so that ฉันอธิบายเหตุผลให้ลูกค้าได้เมื่อเขาถาม
22. As a พนักงานขาย, I want to ระบุว่าลูกค้าคนนี้เป็นลูกค้า B2B ของร้านได้, so that ระบบคิดราคาให้ถูกชั้นโดยไม่ต้องแก้ทีละรายการ

### ผู้จัดการแคตตาล็อก / ผู้ดูแลสินค้า

23. As a ผู้ดูแลสินค้า, I want to สร้างสินค้าใหม่โดยกำหนดหน่วยพื้นฐานได้หนึ่งหน่วย, so that ระบบนับสต็อกและคิดราคาได้ตรงกับความจริง
24. As a ผู้ดูแลสินค้า, I want to เพิ่มหน่วยขายเป็นตัวคูณจำนวนเต็มของหน่วยพื้นฐานได้หลายหน่วย, so that ลูกค้าเลือกสั่งได้ทั้งแบบถุงและแบบพาเลต
25. As a ผู้ดูแลสินค้า, I want to กำหนดหน่วยวัดพร้อมอัตราแปลงจากหน่วยพื้นฐานเพื่อแสดงผลช่วยคิน, so that ลูกค้าที่คิดเป็นตร.ม. เข้าใจสินค้าโดยไม่ต้องแปลงเอง
26. As a ผู้ดูแลสินค้า, I want to ตั้งราคาปลีกและราคาส่งต่อหน่วยพื้นฐานได้, so that ฉันกำหนดราคาได้ตรงกับที่ร้านขายจริง
27. As a ผู้ดูแลสินค้า, I want to ตั้งเกณฑ์ปริมาณต่อสินค้าได้, so that ฉันกำหนดได้ว่าต้องซื้อเท่าไรถึงเข้าเกณฑ์ราคาส่ง
28. As a ผู้ดูแลสินค้า, I want to ตั้งส่วนลดปริมาณเป็นช่วงจำนวนหน่วยพื้นฐานพร้อมอัตราส่วนลด, so that ลูกค้าได้ราคาถูกลงเมื่อซื้อมากขึ้น
29. As a ผู้ดูแลสินค้า, I want to ตั้งราคาเฉพาะลูกค้าให้ลูกค้า B2B แต่ละรายได้ โดยระบุเฉพาะสินค้าที่ต้องการ, so that ฉันให้ราคาพิเศษเฉพาะรายที่ตกลงไว้
30. As a ผู้ดูแลสินค้า, I want to ระบบเตือนเมื่อฉันพยายามตั้งหน่วยพื้นฐานให้สินค้าที่มีอยู่แล้วมากกว่าหนึ่งหน่วย, so that ฉันไม่สร้างข้อมูลที่ขัดกับหลักของระบบ
31. As a ผู้ดูแลสินค้า, I want to เตือนถ้าฉันตั้งตัวคูณหน่วยขายที่ไม่ลงตัว, so that ฉันไม่ตั้งค่าที่ระบบปฏิเสธ
32. As a ผู้ดูแลสินค้า, I want to แยกสินค้าที่ต่างกันที่ราคา สต็อก หรือหน่วยขายออกเป็นคนละสินค้า, so that ข้อมูลของแต่ละรุ่นไม่ปนกัน
33. As a ผู้ดูแลสินค้า, I want to รวมตัวเลือกที่เหมือนกันทุกอย่างไว้ใต้สินค้าเดียว เช่น สีของสายไฟ, so that ฉันไม่ต้องสร้างรายการซ้ำ
34. As a ผู้ดูแลสินค้า, I want to ดูว่าสินค้าใดถูกตั้งหน่วยวัดไว้ และอัตราแปลงเป็นอะไร, so that ฉันตรวจความถูกต้องของข้อมูลที่ลูกค้าเห็น
35. As a ผู้ดูแลสินค้า, I want to ปิดสินค้าที่หมดจากการแสดงผลได้โดยไม่ต้องลบประวัติ, so that ออเดอร์เก่ายังอ้างอิงสินค้าได้

### ผู้บริหาร / เจ้าของร้าน

36. As a เจ้าของร้าน, I want to ดูว่าส่วนลดปริมาณทำให้ร้านขาดทุนหรือไม่ โดยเห็นราคาที่คำนวณจริง, so that ฉันปรับเกณฑ์ได้โดยไม่ต้องคำนวณเอง
37. As a เจ้าของร้าน, I want to ยืนยันว่าราคาที่ลูกค้าเห็นกับราคาที่ระบบเก็บได้ตรงกันเสมอ, so that ฉันไม่มีข้อโต้แย้งเรื่องราคากับลูกค้า
38. As a เจ้าของร้าน, I want to เปลี่ยนราคาปลีกของปูนแล้วมีผลกับทุกหน่วยขายของปูน, so that ฉันแก้ราคาที่เดียวไม่ต้องไล่แก้ทีละหน่วย
39. As a เจ้าของร้าน, I want to ยอดทุกออเดอร์ออกมาเป็นจำนวนเต็มเสมอ ไม่มีเศษสตางค์หลงเหลือ, so that ยอดขายตรงกับเงินจริงที่ได้
40. As a เจ้าของร้าน, I want to เห็นราคาส่งของลูกค้าแต่ละรายได้, so that ฉันตรวจสอบได้ว่าราคาที่ตั้งไว้ถูกต้อง
41. As a เจ้าของร้าน, I want to ลูกค้าที่ซื้อครบเกณฑ์ปริมาณได้ราคาส่งอย่างสม่ำเสมอ ไม่ขึ้นกับคนที่ให้ราคา, so that ฉันไม่ต้องเดาว่าจะให้ราคากับใคร

## Implementation Decisions

### หน่วยและปริมาณ

1. **หนึ่งสินค้ามีหน่วยพื้นฐานเพียงหนึ่งหน่วย** ระบบต้องปฏิเสธการกำหนดหน่วยพื้นฐานเพิ่ม หน่วยพื้นฐานมีตัวคูณเท่ากับ 1 เสมอ และเป็นหน่วยที่นับสต็อกได้ เหตุผลและผลกระทบดูที่ `docs/adr/0003-เกณฑ์แยกสินค้า.md` และคำนิยามใน `GLOSSARY.md`

2. **หน่วยขายเป็นตัวคูณจำนวนเต็มของหน่วยพื้นฐาน ไม่ใช่ภาชนะจัดเก็บ** เช่น หน่วยขาย "พาเลต" ของปูนมีตัวคูณ 40 หมายความว่า 1 พาเลต = 40 ถุงเสมอ ไม่ว่าของจะครบก้อนหรือไม่ ต้องแยกความหมายของหน่วยขายออกจากภาชนะจัดเก็บในโมเดลข้อมูลอย่างชัดเจน เพราะสองอย่างนี้ไม่ได้แปลกัน ดู `docs/adr/0002-หน่วยขายเป็นตัวคูณ-ไม่ใช่ภาชนะ.md`

3. **ระบบไม่รับปริมาณเป็นเศษ** ปริมาณที่รับได้ต้องเป็นจำนวนเต็มเสมอ ระบบต้องปฏิเสธค่าที่ไม่ใช่จำนวนเต็มที่ชัดเจน ไม่มีการปัดขึ้นหรือปัดลงที่ใดในระบบ ดู `docs/adr/0001-ขายเฉพาะจำนวนเต็ม.md`

4. **หน่วยวัดเป็นข้อมูลแสดงผลเท่านั้น** ไม่ใช่หน่วยที่ขายและไม่ใช่หน่วยที่รับเป็นปริมาณ หน่วยวัดถูกตั้งค่าพร้อมอัตราแปลงจากหน่วยพื้นฐาน เพื่อแสดงความสัมพันธ์ให้ลูกค้า เช่น "1 กล่อง = 1.44 ตร.ม." ระบบต้องไม่นำหน่วยวัดไปเข้าสู่การคำนวณราคาหรือการคิดเกณฑ์ใดทั้งสิ้น

5. **การแปลงปริมาณเป็นหน่วยพื้นฐานเป็นการคูณอย่างเดียว** จำนวนหน่วยพื้นฐาน = จำนวนที่กรอก × ตัวคูณของหน่วยขายที่เลือก การแปลงจึงย้อนกลับได้เสมอ และไม่มีการสูญเสียความแม่นยำ

### โครงสร้างสินค้า

6. **ไม่มีโครงสร้างสองชั้น (สินค้า > ตัวเลือก)** สินค้าคือหน่วยที่ขายและนับสต็อกได้จริง ตัวเลือก (เช่น สีของสายไฟ) เป็นเพียงข้อมูลประกอบที่ไม่มีราคา สต็อก หรือหน่วยขายของตัวเอง ตัวเลือกใดที่ต้องการราคา สต็อก หรือหน่วยขายต่างออกไป ต้องแยกเป็นคนละสินค้า

7. **เกณฑ์การแยกสินค้าคือราคา สต็อก หรือหน่วยขาย** ถ้าสองอย่างต่างกันในสามสิ่งนี้ ให้ถือเป็นคนละสินค้า หากต่างกันที่ขนาดจนหน่วยขายไม่เหมือนกัน ต้องถือเป็นคนละสินค้าเสมอ เพราะข้อ 1 กำหนดหน่วยพื้นฐานได้หนึ่งหน่วย

### ราคา

8. **ราคาทุกตัวเป็นต่อหน่วยพื้นฐานเสมอ** ไม่มีการเก็บราคาแยกตามหน่วยขาย ผลที่ตามมา: เมื่อเปลี่ยนราคาปลีกของสินค้าหนึ่ง ราคาของทุกหน่วยขายของสินค้านั้นเปลี่ยนตามทันที และไม่มี "ราคาพาเลต" ที่ต้องซิงก์กับราคาถุง

9. **มีชั้นราคาสามระดับ เรียงตามความสำคัญ** ได้แก่ ราคาเฉพาะลูกค้า → ราคาส่ง → ราคาปลีก ราคาเฉพาะลูกค้าทับราคาส่งเสมอเมื่อมี ไม่ต้องมีราคาเฉพาะลูกค้าครอบทุกชั้น

10. **เกณฑ์ปริมาณและส่วนลดปริมาณเป็นคนละกลไก** เกณฑ์ปริมาณเป็นเงื่อนไขขั้นต่ำที่คุมว่าใครได้รับราคาส่ง ส่วนลดปริมาณเป็นการลดราคาเพิ่มเติมตามจำนวนที่ซื้อ กลไกทั้งสองคิดจากจำนวนหน่วยพื้นฐานเหมือนกัน แต่เก็บแยกจากกันในโมเดล

11. **การได้ราคาส่งต้องเป็นไปตามสองเงื่อนไขพร้อมกัน** คือ (ก) ลูกค้าต้องเป็นลูกค้า B2B และ (ข) จำนวนหน่วยพื้นฐานที่ซื้อต้องถึงเกณฑ์ปริมาณของสินค้านั้น ลูกค้าปลีกจึงไม่มีทางเข้าเกณฑ์ราคาส่งด้วยการสั่งปริมาณมาก ป้องกันการเก็งกำไรราคาส่ง

12. **ส่วนลดปริมาณคิดจากจำนวนหน่วยพื้นฐานที่ซื้อจริง** ไม่ขึ้นกับว่าลูกค้าเลือกหน่วยขายใด ลูกค้าที่สั่ง 80 ถุงและลูกค้าที่สั่ง 2 พาเลตต้องได้ส่วนลดเท่ากัน ดู `docs/adr/0004-ส่วนลดผูกกับจำนวน-ไม่ใช่หน่วยขาย.md`

13. **ไม่มี "ราคาพาเลต" ในระบบ และห้ามสร้างเพิ่ม** หน่วยขายเป็นเพียงตัวช่วยกรอกจำนวน ไม่ใช่ช่องทางที่ทำให้ได้ราคาถูกกว่า ตารางราคาต่อหน่วยขายจะขัดกับหลักข้อ 12 ทันที

14. **ทุกจำนวนเงินเก็บเป็นจำนวนเต็มหน่วยสตางค์** ไม่ใช้เลขทศนิยม ดู `docs/adr/0005-เก็บเงินเป็นจำนวนเต็ม.md`

15. **ลำดับการคำนวณในการคิดราคารายการ** เป็นลำดับตายตัว ต้องไม่สลับ:
    1. แปลงปริมาณที่กรอกเป็น **จำนวนหน่วยพื้นฐาน** โดยคูณกับตัวคูณของหน่วยขายที่เลือก
    2. เลือกชั้นราคาจาก 3 ชั้น ตามลำดับความสำคัญ โดยพิจารณาเงื่อนไขข้อ 11
    3. หาช่วงส่วนลดปริมาณจากจำนวนหน่วยพื้นฐานที่ได้ แล้วคิดราคาต่อหน่วยหลังลด
    4. คูณราคาต่อหน่วยหลังลดด้วยจำนวนหน่วยพื้นฐาน เพื่อได้ยอดของรายการ

16. **ราคาต่อหน่วยหลังลดต้องเป็นจำนวนเต็มสตางค์ก่อนคูณกับจำนวน** เพราะการคูณจำนวนเต็มสองตัวให้ผลลัพธ์เป๊ะ หากส่วนลดทำให้ราคาต่อหน่วยไม่ลงจำนวนเต็ม ต้องตัดสินใจทิศทางการปัดเพียงจุดเดียว (ดูประเด็นที่ 2 ใน Further Notes)

17. **ต้องคืนทั้งจำนวนหน่วยพื้นฐานและยอดของรายการ** เพื่อให้ผู้เรียกใช้แสดงผลและตรวจสอบได้โดยไม่ต้องคำนวณซ้ำ และเพื่อให้การทดสอบสามารถสังเกตผลของการแปลงหน่วยผ่านจุดเดียวกันนี้ได้

### จุดที่ตัดสินใจเป็น interface

18. **การคิดราคารายการเป็นจุดเดียวที่ทั้งระบบต้องผ่าน** ไม่มีตำแหน่งอื่นที่คำนวณราคา ราคา ส่วนลด หรือเกณฑ์ใดได้ จุดนี้รับข้อมูลเข้าที่เป็นข้อมูลดิบ ไม่มีการอ่านฐานข้อมูลเอง และไม่มีผลข้างเคียง

19. **interface ของการคิดราคารายการรับ "จำนวนหน่วยพื้นฐานที่จะใช้ตัดสินใจเรื่องเกณฑ์" เป็นอินพุตแยก** ค่านี้โดยปกติเท่ากับจำนวนหน่วยพื้นฐานของรายการนั้น แต่การแยกเป็นอินพุตชัดเจนเปิดทางให้ผู้เรียกใช้ส่งจำนวนรวมของทั้งออเดอร์เข้ามาแทนได้ หากภายหลังตัดสินว่าเกณฑ์ปริมาณนับทั้งออเดอร์ (ดูประเด็นที่ 1 ใน Further Notes) โดยไม่ต้องเพิ่ม seam ใหม่ การเปลี่ยนแค่ค่าอินพุตจุดเดียว

20. **สถานะ B2B ของลูกค้าเป็นข้อมูลเข้าของ interface ไม่ใช่เงื่อนไขที่ซ่อนอยู่ภายใน** ต้องส่งข้อมูลความเป็น B2B มาพร้อมกัน เพื่อให้ผลการคิดราคาขึ้นกับข้อมูลที่ส่งเข้าเท่านั้น ไม่ขึ้นกับการค้นหาสถานะจากที่อื่นในระบบ

21. **ชั้นราคาที่ถูกเลือกต้องคืนกลับมาด้วย** เพื่อให้หน้าจอและพนักงานขายอธิบายเหตุผลของราคาได้ และเพื่อให้ผู้ดูแลตรวจสอบว่าราคาเฉพาะลูกค้าทับราคาส่งอยู่จริง

### การตรวจสอบข้อมูลที่ต้องบังคับ

22. ปฏิเสธการกำหนดหน่วยพื้นฐานมากกว่าหนึ่งหน่วยต่อหนึ่งสินค้า
23. ปฏิเสธตัวคูณของหน่วยขายที่ไม่เป็นจำนวนเต็ม
24. ปฏิเสธปริมาณที่กรอกเข้ามาที่ไม่ใช่จำนวนเต็ม
25. ปฏิเสธหน่วยขายที่มีตัวคูณเท่ากับหรือน้อยกว่าหน่วยพื้นฐาน เพราะจะทำให้ตัวแปลงจำนวนไม่ฉีกลับได้
26. ปฏิเสธอัตราแปลงหน่วยวัดที่ไม่ใช่จำนวนบวก
27. ปฏิเสธการตั้งราคาเฉพาะลูกค้าสำหรับสินค้าที่ยังไม่มีราคาปลีกหรือราคาส่ง
28. ปฏิเสธช่วงส่วนลดปริมาณที่ต่ำกว่าขอบบนของช่วงก่อนหน้า เพราะจะทำให้ตารางส่วนลดไม่มีความหมาย

## Testing Decisions

### ลักษณะของเทสต์ที่ดี

- ทดสอบเฉพาะพฤติกรรมภายนอกที่มองเห็นได้จากผลลัพธ์ของการคิดราคารายการ ได้แก่ **จำนวนหน่วยพื้นฐาน**, **ชั้นราคาที่ถูกเลือก** และ **ยอดของรายการ**
- ตั้งชื่อเทสต์และข้อมูลตัวอย่างด้วยศัพท์ใน `GLOSSARY.md` ให้ตรงทุกจุด เช่น "พาเลต" "ถุง" "หน่วยพื้นฐาน" "ราคาส่ง" "เกณฑ์ปริมาณ" ไม่ใช้คำทั่วไปอย่าง "item" หรือ "bulk"
- ไม่ยืนยันรายละเอียดภายใน เช่น โครงสร้างตาราง ชื่อคอลัมน์ ลำดับการทำงานภายใน หรือจำนวนครั้งที่ถูกเรียก ถ้าเทสต์จำเป็นต้องรู้รายละเอียดเหล่านั้น แปลว่า interface ถูกออกแบบมาให้ทดสอบยากเกินไป
- การทดสอบแต่ละกรณีต้องอ่านออกได้ว่ากำลังพิสูจน์กติกาธุรกิจข้อใด ไม่ใช่แค่ยืนยันตัวเลข

### ขอบเขตการทดสอบ

29. **มี seam เดียว: การคิดราคารายการ** ไม่มีเทสต์ที่ผ่าน HTTP handler เพราะยังไม่ได้ตัดสินใจเรื่องฐานข้อมูลและการยืนยันตัวตน การเทสต์ผ่านชั้นเหนือ seam จะต้องเปลี่ยนโครงสร้างทุกครั้งที่ฐานข้อมูลเปลี่ยน

30. **การแปลงหน่วยถูกทดสอบผ่าน seam เดียวกัน** โดยสังเกตที่จำนวนหน่วยพื้นฐานที่คืนกลับมา ไม่เปิด seam แยกสำหรับการแปลงหน่วย เพราะผลของการแปลงปริมาณสู่การคิดราคาอยู่ในผลลัพธ์เดียวกันอยู่แล้ว

31. **ฝั่งอ่าน (หน้าสินค้า) ยังไม่มีการทดสอบในสเปกนี้** เป็นผลตัดสินใจที่รับรู้: เราเชื่อว่าข้อมูลหน่วยวัดและรายการหน่วยขายที่แสดงผลมาจากข้อมูลชุดเดียวกับที่ seam ใช้ หากภายหลังพบว่าหน้าจอสร้างข้อมูลเอง ต้องเพิ่ม seam ที่สองในเวลานั้น ไม่ใช่ตอนนี้

32. **prior art: ไม่มี** โครงสร้างโปรเจกต์ยังไม่มีโค้ดและไม่มีชุดเทสต์เดิม เทสต์ชุดแรกจึงเป็นการกำหนดรูปแบบมาตรฐานของโปรเจกต์ แนวปฏิบัติที่ควรยึดคือการเขียนเทสต์เป็นตารางกรณี กรณีละหนึ่งบรรทัด เมื่อกติกาตัดสินใจยาวหลายข้อ

### กรณีที่ต้องครอบคลุม

33. **การแปลงหน่วย**: หน่วยพื้นฐานถูกเลือกโดยตรง · พาเลต 1 หน่วย = 40 ถุง · พาเลต 2 หน่วย = 80 ถุง · ตัวคูณที่ไม่ใช่เลขกลม เช่น 3 หน่วย = 120 ถุง
34. **ไม่มีการปัดเศษ**: ระบบไม่มีเส้นทางที่ผลลัพธ์เป็นเศษ และการปฏิเสธปริมาณเศษต้องถูกปฏิเสธตั้งแต่ชั้นรับข้อมูล
35. **ความเท่ากันของหน่วยขาย**: ลูกค้าที่สั่ง 80 ถุง กับลูกค้าที่สั่ง 2 พาเลต ต้องได้ชั้นราคา ส่วนลดปริมาณ และยอดของรายการที่เหมือนกันทุกประการ นี่คือเทสต์ที่พิสูจน์หัวใจของ ADR-0004
36. **ลำดับชั้นราคา**: ลูกค้าปลีกได้ราคาปลีก · ลูกค้า B2B ที่ซื้อไม่ครบเกณฑ์ปริมาณได้ราคาปลีก · ลูกค้า B2B ที่ซื้อครบเกณฑ์ปริมาณได้ราคาส่ง · ลูกค้า B2B ที่มีราคาเฉพาะลูกค้าได้ราคาเฉพาะลูกค้าแม้จะซื้อครบเกณฑ์ปริมาณ
37. **ราคาเฉพาะลูกค้าทับราคาส่ง**: ลูกค้าที่มีราคาเฉพาะลูกค้าต้องได้ราคาเฉพาะลูกค้าเสมอ ไม่ว่าจะซื้อมากแค่ไหน และลูกค้าที่มีราคาเฉพาะลูกค้าเฉพาะสินค้าหนึ่งต้องได้ราคาปกติสำหรับสินค้าอื่น
38. **เกณฑ์ปริมาณเป็นแบบเส้นตรง ไม่ใช่ชั้นบันได**: ลูกค้า B2B ที่ซื้อต่ำกว่าเกณฑ์ปริมาณแต่เพิ่งข้ามเส้นอยู่ในระดับเดียวกับคนที่ซื้อมากกว่าเกณฑ์ปริมาณมาก
39. **ส่วนลดปริมาณเป็นช่วง**: จำนวนที่อยู่ในช่วงต้องได้ส่วนลดของช่วงนั้น · จำนวนที่ต่ำกว่าขอบล่างของช่วงแรกต้องไม่ได้ส่วนลด · จำนวนที่สูงกว่าขอบบนของช่วงสุดท้ายต้องได้ส่วนลดของช่วงสุดท้าย
40. **ความแม่นยำของเงิน**: ผลลัพธ์ทุกกรณีต้องเป็นจำนวนเต็มสตางค์ · ต้องไม่มีเศษหลง · การคำนวณต้องให้ผลเหมือนกันทุกครั้ง (ทำซ้ำได้)
41. **เงื่อนไขที่ต้องถูกปฏิเสธ**: ปริมาณเศษ · หน่วยขายที่ตัวคูณเป็นศูนย์หรือติดลบ · สินค้าที่ยังไม่มีราคาที่เลือกได้เลย
42. **สินค้าที่ไม่มีส่วนลดปริมาณ**: สินค้าที่ไม่ได้ตั้งส่วนลดปริมาณไว้ต้องคิดได้ตามปกติด้วยชั้นราคาที่เลือก
43. **กรณีที่ยังไม่ได้ตัดสินและต้องถามคนอ่านโค้ด**: ต้องมีเทสต์ยืนยันเสมอว่าหน่วยวัดไม่เคยส่งผลต่อราคา — เช่น สินค้าที่มีหน่วยวัดต้องให้ยอดเท่ากับสินค้าที่ไม่มีหน่วยวัดเมื่อข้อมูลอื่นเท่ากัน เพราะนี่คือข้อกำหนดที่คนอ่านโค้ดจะพลาดที่สุด

## Out of Scope

- **สินค้าราคาผันผวนและสินค้าที่ให้สอบถามราคา** เช่น เหล็กที่ราคาขึ้นลงตามตลาด ต้องออกแบบว่าจะแสดงราคา ซ่อนราคา หรือเปลี่ยนเป็นสินค้าที่ต้องสอบถาม
- **การจัดกลุ่มสินค้าที่ถูกแยกเป็นหลายรายการ** เมื่อสินค้าต่างกันที่ราคา สต็อก หรือหน่วยขาย จะถูกแยกเป็นคนละสินค้า ลูกค้าจึงเห็นรายการที่ชื่อคล้ายกันหลายแถว วิธีจัดกลุ่มและการนำทางผู้ใช้ยังไม่ได้ตัดสิน
- **ค่าขนส่ง ค่าตัดเหล็ก และค่าใช้จ่ายอื่น** ว่าจะถือเป็นสินค้า บริการ หรือส่วนเพิ่มของรายการ
- **ตะกร้าสินค้าและการชำระเงิน** เฉพาะการคิดราคารายการเท่านั้น ไม่รวมการสรุปยอดทั้งออเดอร์
- **ใบเสนอราคา เครดิต และการวางบิลของ B2B**
- **สินค้าคงคลังและการจองสต็อก** การนับสต็อกในหน่วยพื้นฐานเป็นผลที่ตามมาของข้อ 1 แต่กติกาการจองสต็อกและการจัดการหลายคลังอยู่คนละสเปก
- **ภาษีและเอกสารภาษี** รวมถึงคำถามว่าราคาที่แสดงผลรวม VAT หรือไม่
- **บัญชีผู้ใช้และการกำหนดบทบาท** สเปกนี้รับ "สถานะ B2B ของลูกค้า" เป็นข้อมูลเข้าที่ส่งมาให้ ระบบที่ให้ความสามคัญกับการสร้างและอนุมัติสถานะนั้นอยู่คนละสเปก
- **การเลือกฐานข้อมูลและการยืนยันตัวตน** ยังไม่ได้ตัดสิน จึงไม่มีการออกแบบชั้นจัดเก็บข้อมูลหรือสคีมาคงที่ในสเปกนี้
- **การขายเป็นเศษ** ถูกตัดออกโดย ADR-0001 และถ้าต้องการ ต้องทำเป็น ADR ฉบับใหม่

### สิ่งที่ตกลงกันแล้วในสเปกนี้แต่ไม่ได้มาจากการ grill

**เก็บเงินเป็นจำนวนเต็มหน่วยสตางค์** (ข้อ 14) ไม่ได้ถูกตัดสินใจในเซสชัน grill แต่ถูกระบุเป็นข้อกำหนด และได้เขียนเป็น ADR-0005 แล้ว เนื่องจากโครงสร้างราคาเอื้อให้อยู่แล้ว (ราคาต่อหน่วยพื้นฐาน × จำนวนเต็ม) ผลที่ได้จึงเป๊ะโดยไม่ต้องปัดเศษที่ใดเลย ซึ่งสอดคล้องกับหลักการเดียวกับ ADR-0001

### ประเด็นที่ยังต้องตัดสินก่อนลงมือทำ

1. **เกณฑ์ปริมาณและส่วนลดปริมาณนับเป็นรายการเดียว หรือทั้งออเดอร์** ยังไม่ได้ตัดสิน การเลือก seam เดียว (การคิดราคารายการ) ไปเงื่อนไขโดยปริยายว่านับรายการเดียว แต่ข้อ 19 ใน Implementation Decisions ออกแบบให้รองรับการส่งจำนวนรวมของทั้งออเดอร์เข้ามาแทนได้ จึงยังไม่ปิดทาง หากภายหลังเลือก "ทั้งออเดอร์" จะไม่ต้องเพิ่ม seam ใหม่ แต่ต้องระบุว่าจะนับรวมทั้งออเดอร์หรือเฉพาะสินค้าชนิดเดียวกัน
2. **ทิศทางการปัดเมื่อราคาต่อหน่วยหลังลดไม่ลงจำนวนเต็มสตางค์** เช่น ราคาปลีก 190 บาท ลด 7.5% = 175.75 บาท ต้องตัดสินว่าปัดลงเป็น 175.75 → 175 (เข้าข้างร้าน) หรือปัดขึ้นเป็น 176 (เข้าข้างลูกค้า) จุดนี้มีผลต่อความเชื่อถือของราคาที่แสดงผล จึงควรให้ผู้มีอำนาจตัดสิน ไม่ใช่ปล่อยให้ผู้ลงมือทำเลือกเอง
3. **อัตราส่วนลดปริมาณสะสมกับราคาเฉพาะลูกค้าหรือไม่** ถ้าลูกค้ามีราคาเฉพาะลูกค้าอยู่แล้ว ส่วนลดปริมาณยังถูกนำมาใช้ต่ออีกหรือไม่ ไม่ได้ตัดสิน
4. **หน่วยวัดแสดงผลพร้อมกันได้กี่หน่วยวัดต่อหนึ่งสินค้า** เช่น กระเบื้องที่รู้ทั้ง ตร.ม. และ จำนวนแผ่น ยังไม่ได้ตัดสิน รวมถึงสูตรแปลงที่ไม่ใช่การคูณ เช่น "ปริมาณต่อห้อง = พื้นที่ ÷ พื้นที่ต่อแผ่น"
5. **การแสดงราคาต่อหน่วยขายบนหน้าสินค้า** จะแสดงเฉพาะราคาต่อหน่วยพื้นฐาน หรือคำนวณราคาต่อหน่วยขายให้ด้วย การคำนวณราคาต่อหน่วยขายต้องระวังไม่ให้สื่อว่ามี "ราคาพาเลต" ตาม ADR-0004

### ผลกระทบต่อการทำงานที่ยังไม่ได้ตัดสิน

- สเปกนี้ไม่ได้ระบุฐานข้อมูล เพราะยังไม่ได้ตัดสิน แต่โมเดลข้อมูลที่ต้องรองรับถูกกำหนดไว้แล้วในข้อ 1–13 ซึ่งไม่ขึ้นกับตัวเลือกฐานข้อมูล
- การทดสอบไม่ต้องการฐานข้อมูลเลย เพราะ interface ของการคิดราคารายการเป็นข้อมูลเข้า–ข้อมูลออกล้วน ตัดสินใจเรื่องฐานข้อมูลจึงไม่ทำให้ชุดเทสต์ชุดนี้ต้องเขียนใหม่
- การคืนชั้นราคาที่ถูกเลือก (ข้อ 21) ทำให้หน้าจอสามารถแสดงเหตุผลของราคาได้โดยไม่ต้องทำตรรกะซ้ำ ควรถือเป็นข้อผูกพันระหว่างสเปกนี้กับสเปกหน้าตะกร้า
